# Governance

A simple way to run the hub in the open. Change it as your group grows, and record changes in a pull request so everyone can see them.

## Roles

- **Participants** are anyone who claims a task, files a report, joins a chapter or takes part in discussion.
- **Chapter leads** keep a chapter's issue up to date, welcome newcomers and help people find tasks.
- **Maintainers** have write access. They triage issues, verify reports, review pull requests and enforce the code of conduct. Aim for at least three, in different places, so the project does not depend on one person.

## Verifying reports

Reported numbers count as "reported". A maintainer adds the `verified` label when the report has been checked. Agree these rules in public:

1. What counts as evidence: a bill summary, a meeting record, a news story, a photo, a letter from a partner organisation.
2. A report is checked by someone other than its author.
3. Estimates are accepted when the method is explained.
4. If a figure is later found to be wrong, remove `verified` and correct the report.

## Deciding things

- **Small changes** (wording, a new task, a fixed link): any maintainer can merge after one review.
- **Larger changes** (new goals, changes to targets, changes to these rules): open an issue, leave it open for at least seven days, and merge when maintainers agree and objections have been answered.
- **Targets and baselines** are proposals. When evidence changes, change them, and say why in the pull request.

## Handling disagreement

Where the plan names real trade-offs, such as how to fund an income floor, document the options and their costs rather than choosing a side for everyone. Chapters may choose different options for their own area.

## Keeping the data honest

- Every goal figure links to a source in its issue or pull request.
- The `verified` label is the only thing that moves a number into the verified column.
- `docs/data/progress.json` is generated by an Action. Do not edit it by hand.
